# Security and Privacy

## Purpose

Every row in the database belongs to exactly one user, and no code path should ever let one user read or modify another user's data. Beyond that basic isolation guarantee, the system needs a small number of privileged operations — deleting an account, exporting all data, recording compliance audit events — that require elevated authority without handing that authority to the client. This section describes how those two problems are solved and how the DPDP-oriented deletion flow keeps a verifiable audit record even after the user's identity is gone.

## What the user experiences

From a user's perspective, the security model is invisible until they need it. If they open the app on a different device, they see only their own data. If they tap "Erase data" in Settings, everything disappears and onboarding resets — but they are still logged in. "Everything" now includes their name, date of birth and gender in the sign-in record, their own error reports, and what the app keeps on the device (the chat conversation, saved dismissals, lock settings, scheduled reminders and any export file left in the cache). If they tap "Delete account", their login is removed and they are signed out. In both cases they receive no error, no partial state, and no confirmation that anyone else's data was involved.

Two other things can happen to a reader who has been here a while. When the terms or privacy policy change materially, or when they never gave the separate health-data consent, the next visit lands on a calm "we have updated our terms" screen before anything else; accepting returns them to Home, and "Not now" leads to Settings where they can export or delete instead. And Settings carries a "Withdraw consent" row: since a ledger cannot be kept without consent to process health information, withdrawing explains that the data goes, offers an export first, then erase or delete.

The other visible privacy surface is the data export: a JSON file containing every log, goal, brand, reminder, setting, audit event, error report, profile field and the sign-in record (email, phone, account dates) that belongs to them. The export paginates in chunks of 5 000 rows and produces a `truncated: true` flag if the safety cap of 200 pages is ever reached (roughly 270 years of daily use at 10 sticks per day — effectively never).

## How it works

### The RLS model

Every table in the `public` schema has Row Level Security enabled. This was confirmed live against project `tvcwrsglceahkjnfuzkn` on 2026-06-19 — all 13 base tables have `relrowsecurity = true`:

`audit_events`, `brand_variants`, `brands`, `cigarette_logs`, `error_events`, `goals`, `price_entries`, `rate_limit_counters`, `reminders`, `settings_kv`, `usage_events`, `user_facts_seen`, `user_profiles`.

The policy shape for most user-owned tables is a single FOR ALL policy that gates both `USING` and `WITH CHECK` on `user_id = (select auth.uid())`. The `(select ...)` wrapper is important: it causes Postgres to evaluate `auth.uid()` once as an InitPlan rather than once per row, which matters for table scans on large log sets. The rewrite was applied in `supabase/migrations/20260602000000_perf_rls_initplan_indexes.sql:22–46`.

`rate_limit_counters` is the exception. It has RLS enabled but carries no policy at all, making it default-deny to every non-service-role caller. Only the `consume_rate_limit` SECURITY DEFINER function can touch it, and that function is granted only to `service_role`. An anon `SELECT` returns `42501`. This table is intentionally invisible to both `anon` and `authenticated` roles — nothing about its contents should ever be client-readable.

**Realtime is gated by the same RLS.** `cigarette_logs`, `goals`, `user_profiles`, `brands`, and `brand_variants` are in the `supabase_realtime` publication (`supabase/migrations/20260620130000_realtime_enable.sql`, brands added in `20260622000000_realtime_brands.sql`). Supabase applies each table's RLS SELECT policy before delivering any `postgres_changes` event to a subscriber, so realtime cannot leak another user's rows — a subscriber only receives changes to rows it could already SELECT (`user_id = auth.uid()` / `id = auth.uid()`). The client-side `filter` is defense-in-depth, not the primary guard. `REPLICA IDENTITY FULL` on the `user_id`-filtered tables affects only the internal WAL stream (so DELETE events carry `user_id`); it exposes nothing extra to clients.

`audit_events` and `error_events` have split policies. `audit_events` allows SELECT (own rows only) but has no INSERT policy for `authenticated` — clients cannot write directly to it; they call Edge Functions which use the service-role client. `error_events` allows SELECT and INSERT for own rows, but has no UPDATE or DELETE policy for `authenticated`, so users cannot modify rows once written. The INSERT policy explicitly blocks `category = 'compliance.delete'` for authenticated users (`supabase/migrations/20260520000000_security_correctness.sql:254–255`).

### SECURITY DEFINER + search_path hygiene

All 16 `SECURITY DEFINER` functions in `public` pin an explicit `search_path`. Fourteen pin `search_path = ''` (the empty string), which means every object reference inside the function body must be schema-qualified or the function errors. Two pin a non-empty path appropriate to their job (the V3 additions `delete_my_usage_events` and `purge_expired_records` both pin `''`):

- `refresh_seed_prices_from_catalog` pins `smoke_seed, public` because it needs to read the seed catalog schema.
- `rls_auto_enable` pins `pg_catalog` because it is a DDL helper that works in system catalogs.

No function inherits the caller's search_path. This matters because a SECURITY DEFINER function runs with the privileges of the function owner (typically the Supabase table owner), not the calling role. If it inherited the caller's search_path, a sufficiently creative caller could shadow `public.some_table` with a same-named table in a schema they control and redirect the function's queries. Pinning to `''` closes that vector entirely. The previous 15 functions were confirmed live via `pg_proc.proconfig` on 2026-06-19.

**anon default-deny.** `20261030000000_security_hardening.sql` revokes every `anon` grant on public tables, sequences and functions, removes the default grants to `anon` for future objects, and drops the built-in PUBLIC `EXECUTE` default for functions the migration role creates. `anon` also inherits `EXECUTE` through PUBLIC on functions that already exist, so every `SECURITY DEFINER` function is revoked `FROM PUBLIC, anon` explicitly (enforced by `src/tests/security-migrations.test.ts`). `scripts/sql/smoke.sql` fails CI if `anon` can execute any public `SECURITY DEFINER` function or holds any public table privilege.

The user-facing RPCs that `authenticated` may call are: `create_log_with_rate_limit`, `delete_my_usage_events`, `erase_account_data`, `export_account_data`, `get_daily_summary`, `get_health_milestones`, `get_random_facts`, `list_logs_page`, `mark_fact_seen`, `refresh_seed_prices_from_catalog`, `seed_default_brands_if_empty`, `sync_default_brand_catalog`.

The service-role-only / internal functions — `consume_rate_limit`, `handle_new_user`, `record_audit_event`, `rls_auto_enable`, `purge_rate_limit_counters`, `purge_expired_records` — have had `EXECUTE` revoked from both `anon` and `authenticated`. `handle_new_user` fires as a trigger on `auth.users`; trigger execution does not require an EXECUTE grant on the function, so signup is unaffected. The former `auth_email_exists` email-existence oracle is dropped by the hardening migration.

Trigger helpers that are `SECURITY INVOKER` need the opposite care. (The one that calls nothing else, `goals_stamp_completed_at()` in `20261103000000_adaptive_goals.sql`, simply has all privileges revoked from `PUBLIC`, `anon` and `authenticated`.) `keep_onboarding_step_monotonic()` (`20261101120000_onboarding_step_monotonic.sql`) runs as the writing role and calls `onboarding_step_rank(text)`, so that helper is explicitly granted to `authenticated` and `service_role` (and revoked from `PUBLIC` and `anon`); revoking it from `authenticated` would make every onboarding step write fail with `42501`. The trigger function itself is revoked from everyone — Postgres checks EXECUTE on a trigger function at `CREATE TRIGGER`, not when it fires. Neither function reads a table, so neither is a tenant-isolation boundary; RLS still decides which rows a user can update.

### The DPDP export and erase RPCs

`export_account_data` (`supabase/migrations/20260521000000_audit_export_ops.sql:29–287`) returns a versioned JSON payload (re-issued by `20261103000000_adaptive_goals.sql`, same signature and grants, to add `completedAt` to each goal; `20261104120000_export_complete.sql` made it version 3). The first page includes profile, brands, goals (with `completedAt`), settings, reminders, price entries, usage events, audit events, facts-seen, the sign-in record (`account`: email, phone, createdAt, lastSignInAt) and the caller's own `errorEvents`. A test asserts the export covers every table erase touches. The import schema accepts versions 2 and 3. Subsequent pages return only the next chunk of cigarette logs, using `(ts_utc, id)` DESC keyset cursors for stable, gap-free pagination. The RPC is bounded: `p_limit` is clamped between 100 and 5 000. Each call to the first page appends an `account_data_exported` row to `audit_events` so there is a record of every export request.

`erase_account_data` (`supabase/migrations/20260521000000_audit_export_ops.sql:303–369`) runs as the calling user (it reads `auth.uid()` internally — the Edge Function intentionally calls it with the user's bearer token, not the service-role client, so `auth.uid()` resolves correctly). It:

1. Computes `user_hash = sha256(uid || ':' || pepper)` using `extensions.digest` and the `app.audit_pepper` GUC (or the Vault secret `audit_pepper`).
2. Rewrites all `audit_events` rows for this user: nulls out `user_id`, replaces `props_json` with `{"hashed_user_id": "<hash>"}`.
3. Deletes all `error_events` rows for this user (they used to be kept with a hashed id).
4. Deletes all product data (logs, brands, variants, goals, reminders, settings, price entries, usage events, facts seen).
5. Resets the profile row, including the otherwise-immutable `full_name`, `date_of_birth`, `gender`, plus `mobile_e164` and `place` (it sets the transaction-local `app.erasing` flag, which `enforce_profile_identity_rules` honours) and `health_data_consent_at` (`20261104130000_health_consent.sql`) and `mobile_changed_at` and any old `deleted_at` stamp (`20261104140000_erase_profile_leftovers.sql`; `country` and `currency` stay as regional settings), removes the same three identity keys from `auth.users.raw_user_meta_data`, and no longer stamps `deleted_at` (`20261104100000_erase_auth_metadata.sql`). The clients then call `refreshSession()` (`src/services/cloudErase.ts`) so the signed-in JWT stops carrying the old `user_metadata`; a failure there is logged and never blocks the erase.
6. Re-seeds default brands via `smoke_seed.apply_default_brands(uid)`.
7. Inserts a final `account_data_erased` audit event with `prior_identity_erased: true` (still attributed to the live user, since auth deletion comes later). That row is the record that the user's earlier name / DOB / gender existed before they re-entered new ones, and the disclosed accountability record of the erasure itself. It is the one thing about the person that outlives an erase, for the 12-month audit retention (see Retention below), and it is why an export taken after an erase is not empty.

After `erase_account_data` returns, the `delete-account` Edge Function calls `auth.admin.deleteUser(userId)`, which cascades through foreign keys and removes anything the erase step missed (defense-in-depth against future schema drift). If `erase_account_data` fails for any reason, the function aborts without calling `deleteUser` — the user's auth row stays intact and they can retry (`supabase/functions/delete-account/index.ts:183–194`).

### The peppered audit hash

The pepper is a 32-byte random secret stored as the `AUDIT_PEPPER` Edge Function environment variable and surfaced inside the DB as the `app.audit_pepper` GUC. Two functions use it:

- `delete-account/index.ts` — `hashWithPepper(user.id, AUDIT_PEPPER)` is written into the compliance delete row in `error_events` before the user is erased, and the IP and the per-user rate-limit key are hashed the same way, so `rate_limit_counters` never holds a raw user id. The function returns `server_misconfigured` (500) if `AUDIT_PEPPER` is unset rather than storing a reversible hash; `send-sms-otp` does the same, since it keys the phone rate-limit bucket on the peppered hash.
- `audit-record/index.ts` — the same hash keys the per-user rate-limit bucket and appears in log output when a user hits the audit-record rate limit.

The hash is computed in `supabase/functions/_shared/hash.ts` using `crypto.subtle.digest('SHA-256', ...)`. The pepper is what makes the retained audit rows non-reversible: once `auth.users` is purged, the hashed id has no public counterpart to correlate against. Rotation of the pepper (procedure in `docs/runbooks/audit-pepper-rotation.md`) severs forensic continuity across the rotation boundary — existing hashes in `error_events` remain inert.

Inside the DB the same `<id>:<pepper>` form is expressed using `extensions.digest` (pgcrypto): `encode(extensions.digest(uid::text || ':' || pepper, 'sha256'), 'hex')` (`20261030000000_security_hardening.sql`). Rows anonymized before that migration used `uid || pepper` with no colon; to correlate one, hash the candidate id both ways.

### Compliance delete row tamper-resistance

A `compliance.delete` row in `error_events` is a surviving trace that a deletion happened (kept 90 days like every `error_events` row; the longer erasure proof is the 12-month `account_data_erased` audit row that `erase_account_data` writes first, which survives the auth-user deletion with `user_id` set to NULL). It is written by the service-role client in `delete-account/index.ts:164–169` with `user_id = null`, so RLS SELECT (which requires `user_id = auth.uid()`) makes it invisible to any authenticated user. Three layers enforce this:

**Layer 1 — RLS INSERT policy.** `error_events_insert` (`supabase/migrations/20260520000000_security_correctness.sql:254–255`) allows authenticated users to insert rows where `user_id = auth.uid() AND category <> 'compliance.delete'`. They cannot insert a null-user row, and they cannot insert a row in the compliance.delete category at all.

**Layer 2 — No UPDATE or DELETE policy.** `authenticated` has no policy for UPDATE or DELETE on `error_events`, so RLS default-deny applies. A user cannot modify or delete any `error_events` row, including rows they wrote themselves.

**Layer 3 — CHECK constraint.** `error_events_compliance_delete_null_user_check` enforces `category <> 'compliance.delete' OR user_id IS NULL` at the DB level. This closes the gap where future code might accidentally insert a user-owned `compliance.delete` row that would then be readable by that user.

Its history is the repo's canonical migrations-can-lie example: the constraint was declared in `20260520000000_security_correctness.sql:271–277`, but that block was edited after the migration had already been applied, so it never reached the live DB. The June 2026 sovereignty audit (`docs/security/sovereignty-audit-2026-06.md:§4`) correctly found it absent; `20260619000000_error_events_compliance_check.sql` (live ledger row `20260619075741`) restored it idempotently. Last verified live via `pg_constraint` on 2026-07-06.

### Service-role-only surfaces

The following are reachable only with the service-role key and are never handed to browser clients:

- `consume_rate_limit` RPC — backs the Edge Function rate limiter; `EXECUTE` granted only to `service_role` (`supabase/migrations/20260523092236_add_rate_limit_counters.sql:62–63`).
- `rate_limit_counters` table — RLS enabled, no policy, hard default-deny to all non-service-role callers. Emails, phone numbers and IPs are stored only as keyed hashes: edge functions use `hashWithPepper(value, AUDIT_PEPPER)` (`_shared/hash.ts`), the web limiter an HMAC keyed on the service-role key. Per-user buckets in `audit-record` and `delete-account` key on the peppered hash of the user id (`user:<hash>`), not the raw UUID, since the V3 work. The hardening migration deletes every pre-hashing row once, enables `pg_cron` (guarded) and schedules `purge_rate_limit_counters()` daily at 03:17 to drop rows older than 2 days. The migration only warns if pg_cron cannot be enabled; `scripts/sql/smoke.sql` fails if pg_cron is installed but the job is missing. Verify production after deploy with `select * from cron.job`.
- `record_audit_event` RPC — `EXECUTE` revoked from `authenticated` in `supabase/migrations/20260521000000_audit_export_ops.sql:295–297`; re-granted only to `service_role`. The `audit-record` Edge Function verifies the caller's JWT with the anon client first, then writes through the service-role client.
- `auth.admin.deleteUser` — called only by `delete-account/index.ts:203`; requires `SUPABASE_SERVICE_ROLE_KEY`, which is an Edge Function secret and a server-side Vercel env var, never a `NEXT_PUBLIC_*` value.

The `audit-record` Edge Function (`supabase/functions/audit-record/index.ts`) validates the incoming bearer token via `supabase.auth.getUser()` on the anon client before touching the service-role client, which means a request without a valid JWT is rejected at line 69 before any write happens. The allowlist of valid event types and categories lives in `supabase/functions/_shared/auditAllowlist.ts:3–28`. Props are redacted through a PII denylist (email, phone, Aadhaar, PAN, OTP, tokens, etc.) in `redactAuditProps` (`supabase/functions/_shared/auditAllowlist.ts:74–101`) and the parallel `_redact_audit_props` SQL function (`supabase/migrations/20260520000000_security_correctness.sql:149–188`).

### Retention: the daily purge

Every server-side record has a stated life, and one job enforces it (owner decision O5). `purge_expired_records()` (`supabase/migrations/20261104110000_retention_purge.sql`, `service_role` only) runs daily at 03:37 under pg_cron and deletes `audit_events` older than 12 months, `error_events` older than 90 days and `usage_events` older than 12 months; the existing 03:17 job still drops `rate_limit_counters` after 2 days. Nothing is deleted for inactivity. The periods live in one object, `RETENTION` (`src/lib/privacy/retention.ts`), which the privacy policy renders and `src/tests/retention-purge.test.ts` compares against the SQL intervals, so the text and the job cannot drift. The retention tiers are therefore: erased at once on request (the ledger, identity, own error reports), 90 days (error reports), 12 months (security records including the erasure proof, and opt-in usage events), 2 days (rate-limit counters).

If pg_cron is missing the migration only warns, which would mean the purge silently never runs. Two checks make that loud: `scripts/sql/smoke.sql` fails CI when pg_cron is installed but `purge-expired-records` is not scheduled, and `scripts/verify-backend.mjs` confirms the function exists and prints the manual `cron.job` query as an owner action.

### Error-log redaction

An error report is diagnostic text, so personal data is removed before it is stored, not after. `redactText` and `redactRoute` (`supabase/functions/_shared/redact.ts`, pure, no lookbehind so Hermes can run it) replace emails, UUIDs, bearer tokens, JWTs, long secret-looking runs, phone numbers and long digit runs, cap the input at 2 000 characters first so the patterns stay linear, and reduce a route to its path with dynamic segments as `:id`. The Deno edge functions import it directly and `src/lib/logger.ts` (web and mobile) imports it by relative path, so every writer to `error_events` shares one implementation. `logClientError` never throws: a redaction or insert failure must not break the screen. Over-redacting a diagnostic is accepted; storing a name or number is not.

### One lifecycle table for what the device keeps

Cleaning up is driven by a registry, not by each screen remembering. `STORES` in `src/lib/privacy/lifecycle.ts` lists every store that can hold something about a reader — the auth cookie, remember-me cookie, chat transcript, first-suggestion stamps, lock keys, the cached brand list, the mobile session, in-memory ledger, notifications, export file, plus the server rows — each with the events that clear it: `signOut`, `erase`, `delete`, `withdraw`, `discreetOn`. Device preferences with nothing personal in them (theme, catalog) are listed too, as kept. `clearWebDevice` (`web/lib/privacy/clearDevice.ts`) and `clearNativeDevice` (`src/lib/privacy/clearDeviceNative.ts`) run `runLifecycleClearers` for the platform and event: every clearer for the event runs, one failing never stops the rest, and the ids that failed come back and are logged as ids only (`reportFailedClears`). A test fails if a store has no clearer or a clearer has no row.

Where each event fires. Sign-out: web `AuthProvider` on `SIGNED_OUT` and the Settings sign-out; on any other null session (expiry, a browser reopened without Remember me) the web `AuthProvider` still clears the localStorage stores (transcript, first-suggestion key) but keeps the auth cookies (`clearWebDevice('signOut', undefined, ['web.authCookie'])`); mobile root layout on `SIGNED_OUT` only, never on `INITIAL_SESSION` with a null session, because that also arrives on an offline cold start and wiping the stored session then would sign the reader out for good. Erase and delete: Settings on both platforms, after the server call succeeds; delete also removes the remember-me cookie, the mobile SecureStore session and in-memory ledger. Withdraw behaves as erase (the reader chooses erase or delete). The mobile erase also cancels scheduled notifications and deletes every export file in the cache. The brand cache (`brands:<uid>`, 600 s) is revalidated rather than dropped, to spare free-tier egress.

### Consent, re-consent and withdrawal

**Health-data consent.** What a reader logs — smoking, spending, mood, craving, notes — is information about their health, so it has its own explicit consent, separate from the terms and privacy ticks: an unticked row with Art 9 wording (`HEALTH_CONSENT_LABEL`, `src/lib/healthConsent.ts`, shared by web and Expo), stored as `user_profiles.health_data_consent_at`. `submitConsentStep` refuses to continue without it, and "stamp all" no longer ticks the optional analytics box. Declining sits beside accepting at the same size, with a note that says truthfully what has and has not been saved.

**Re-consent gate.** `consentsOutdated(profile)` (`src/lib/onboardingSteps.ts`) is true for someone who has consented before but a stored terms, privacy or medical-disclaimer version is older than `LEGAL_VERSIONS`, or `health_data_consent_at` is empty. Versions compare as ISO dates (`versionAtLeast`): a stored version the same or newer counts as current, so a web build and an older store-installed mobile build cannot send a reader back and forth; a legacy non-date value such as `'1'` is outdated. It is never true for someone who has not consented at all and never reads `onboarding_step`, so asking again cannot move the wizard. `needsConsentRefresh(profile, onboarded)` widens it for onboarded readers: a missing required stamp (age, terms, privacy, disclaimer, data processing) also counts, because onboarding is only for readers without `onboarded_at`. `consentGateRedirect` uses it and is the one decision shared by the web middleware, `postAuthDestination`, the Expo index and root guard: an onboarded reader who needs a refresh is sent to `/consent` (web `web/app/consent/`, Expo `app/consent.tsx`); a current reader who opens `/consent` goes home. `/consent`, `/privacy`, `/terms`, `/support`, `/settings`, `/auth`, `/reset-password` and `/api` are exempt, so reading the documents, exporting, withdrawing and signing in never loop. Accepting calls `acceptChangedTerms` (`src/services/onboarding.ts`): one `consent_accepted` audit row, the versions (never lower than the stored ones, plus the health, age and data-processing stamps when missing) stamped in a write that carries no onboarding step, and the `consent.*` settings; the analytics preference is left alone. "Not now" links to Settings, in the same size as Accept. The screen's copy (`src/lib/reconsentCopy.ts`) says what to look for and leaves the detail to the policy; when the terms have not changed and only an age or data-processing stamp is missing, the heading is "Before you continue." and the what-changed list is hidden (`reconsentHeading`).

**What fires it today.** `LEGAL_VERSIONS` is deliberately not bumped yet: that waits on the signed EU representative (`EU_REPRESENTATIVE` in `src/lib/legalEntity.ts`; the pages show a "being appointed" line while it is empty). Until then the gate triggers only for accounts with no `health_data_consent_at`, which after the migration is every existing account; bumping the versions later reaches everyone through the same gate with no further code. `src/tests/legal-release-gate.test.ts` pins the published versions as the baseline: the pages and `docs/legal` must show the `LEGAL_VERSIONS` dates, a later version fails unless every EU representative field is filled, and versions never move backwards.

**Withdrawing.** Settings › Withdraw consent explains that a ledger cannot be kept without the consent, offers the export first (which includes the account email and phone), then "Withdraw and erase my data" or "Withdraw and delete my account". Both emit the existing `consent_revoked` audit type (best-effort, a failed audit write never stands between the reader and their erasure), but only for a withdrawal that happened. Mobile erase runs `recordWithdrawalAfter` (`src/services/consentWithdrawal.ts`), which writes the row after `eraseAllUserData` succeeds, so a failed erase leaves no claim of a withdrawal. Mobile delete sends `{ withdraw: true }` in the body of `delete-account`, and the function writes `consent_revoked` itself (category `compliance`, `user_id` null, props `{ hashed_user_id, reason: 'delete' }`) only after `deleteUser` succeeded, best-effort, because no client can authenticate an audit write once the account is gone, and a cancelled re-auth detour or a failed erase or delete must leave no claim of a withdrawal. The body is strict: empty means false, invalid JSON is 400 `invalid_json`, a non-boolean `withdraw` is 400 `invalid_body`. Both then run the ordinary erase or delete, including the device clears. **Analytics off** is lighter: `saveAnalyticsOptIn(false)` calls `delete_my_usage_events()` first and stores the preference only if that succeeded.

**The operator facts.** Who runs the service lives in one module, `src/lib/legalEntity.ts` (controller and Data Fiduciary Trishit Pal, Grievance Officer with a 30-day response, Kolkata courts, email delivery provider, Anthropic's retention text, helplines), and the rewritten `/privacy` and `/terms` render from it, from `RETENTION` and from `DATA_PROMISES`. `DATA_PROMISES` (`src/lib/privacy/promises.ts`) is the "Our data promises" list; `src/tests/privacy-promises.test.ts` gives every key a checker that reads the code keeping the promise, so a promise cannot be added, or a mechanism removed, without a failing test. The process documents behind the policy (breach runbook, record of processing, DPIA, transfers, processors, retention schedule, owner actions) are in `docs/legal/`.

### Origin allowlist and CORS

Edge Functions check `req.headers.get('origin')` against an allowlist in `supabase/functions/_shared/cors.ts:38–49`. Non-browser clients (native mobile, curl) send no `Origin` header and are accepted — the bearer token is the real gate. In production, `ALLOWED_ORIGINS` must be a comma-separated list of explicit origins; the wildcard `*` is only accepted when `ENVIRONMENT != production`. Disallowed origins receive no `Access-Control-Allow-Origin` header rather than the literal string `'null'`.

### Re-authentication gate on account deletion

`delete-account/index.ts` calls `hasRecentSignIn` (`supabase/functions/_shared/recentAuth.ts`), which reads the presenting access token's own `amr` claim and requires a real sign-in (password, OTP, magic link, recovery, signup) within the configured window (default 15 minutes, tunable via `REAUTH_WINDOW_MIN`). `token_refresh` and `anonymous` never count, and a malformed claim fails closed. The check is bound to the session making the request: the earlier gate read the account-wide `last_sign_in_at`, so a stale stolen session passed whenever the owner had signed in on any other device (security scan F2, 2026-10-30).

On `reauth_required`, web sends the user to `/login?next=/settings?action=delete&reason=reauth` and mobile to `/login?reason=reauth` while they are still signed in. `isReauthRequest` (`src/lib/reauth.ts`) lets exactly that route through web middleware and the mobile `(auth)` layout, which otherwise redirect every signed-in visitor away from `/login`; without it the fresh sign-in the gate demands could never happen and deletion was unreachable.

The detour must then finish the job, or say plainly that it did not. Until 2026-11-02 the mobile login screen ignored `reason`, signed the user in and went Home: the account was never deleted, nothing said so, and the same email and password kept working, which read as "deletion didn't stick". Both platforms now follow one contract from `src/lib/reauth.ts`: the login screen explains why it is asking ("Confirm it's you to finish deleting your account."), mobile hides the email-link mode during re-auth because only a password sign-in refreshes this session's `amr`, and after sign-in both return to `DELETE_RESUME_PATH` (`/settings?action=delete`). Settings consumes that param and opens a second, distinct confirmation, "Signed in again. Delete your account now?"; cancelling shows "Your account has not been deleted." A sign-in alone never deletes anything, so a crafted resume link only ever shows a prompt. On mobile the link is also not enough to get that prompt: `smokeledger://settings?action=delete` can be sent by anyone, so Settings honours it only against a record this device wrote just before the detour. `beginDeleteDetour` (`src/lib/deleteIntent.ts`) stores `{ expiresAt, withdraw, userId }` in SecureStore (`sl.delete.intent.v1`, no AsyncStorage fallback, which could be planted) and refuses to start the detour if it cannot (the error says nothing was deleted). `takeDeleteResume` reads it back, always removes it, and accepts it only for the same user and within `DELETE_INTENT_TTL_MS` (10 minutes, `src/lib/reauth.ts`; malformed, expired, far-future or other-user records are refused). With no valid record the deep link ends in "Your account has not been deleted." The record is the lifecycle row `mobile.deleteIntent` (cleared on sign-out, erase, delete and withdraw), and it also carries the withdraw flag across the detour. The resume confirmation never redirects on a further `reauth_required`, it shows the error, so the flow cannot loop silently. The first confirmation warns "You may be asked to sign in again before anything is deleted." Web detects its own redirect by a flag rather than by swallowing every `authentication_error`, so a real "not signed in" failure is shown. After success web lands on `/?deleted=1` and mobile on `/login?deleted=1`, each with a one-time "Your account and all its data have been deleted." notice (`ACCOUNT_DELETED_PARAM`). Guarded by `src/tests/reauth-route.test.ts`, `src/tests/deleteUserAccount.test.ts` and `web/e2e/account-deletion.spec.ts` (opt-in via `E2E_ALLOW_ACCOUNT_DELETION=1`, throwaway accounts only).

The Edge Function also applies dual rate limiting: per-IP (hashed with SHA-256) and per-user, both capped at 5 requests per 10 minutes. Both use `consume_rate_limit` via the service-role client and fail closed — if the Postgres call fails, the function returns 429 rather than silently disabling the gate.

### Ask the ledger (third-party AI processor)

Ledger Chat is the one place personal data leaves the Supabase/Vercel boundary for a third party. It is opt-in and off by default, on web and on mobile. Both clients talk to one route, `web/app/api/ledger-chat/route.ts`, which is built so that nothing reaches Anthropic unless every gate below has passed, in this order:

1. **Kill switch and release gate.** `LEDGER_CHAT_ENABLED` must be `true` (`web/lib/server/ledgerChat/enabled.ts`); otherwise 503. In Production (`VERCEL_ENV=production`) the code also demands `isChatPolicyLive()` (`src/lib/legal.ts`): `LEGAL_VERSIONS.privacy` must be later than `CHAT_UNDISCLOSED_PRIVACY` (`2026-11-02`), the last policy text that does not describe the chat's full scope. So setting the flag early cannot start the feature, because an opt-in recorded before the bump would rest on the old text. Preview, local and CI runs are not gated, which is how the owner tests before the bump. The web layout and the Settings page read the same `isLedgerChatEnabled()` once and pass a boolean down, so a disabled deployment renders no launcher, no Settings row and no notice, and loads nothing. Mobile has its own build-time switch, `EXPO_PUBLIC_LEDGER_CHAT_ENABLED` (`src/lib/askPill.ts`), which must be `true` and then follows the same gate (`isChatPolicyLive`), except in a development build (`__DEV__`) so the owner can try mobile against Preview; store and EAS preview builds stay gated. When off it hides the pill, the screen and the Settings toggle; a server 503 is shown as a calm "unavailable" line.
2. **Caller.** `resolveChatCaller` (`web/lib/server/ledgerChat/auth.ts`) accepts either a cookie session **plus** `requireSameOrigin` (CSRF), or a native `Authorization: Bearer <Supabase JWT>` verified with `auth.getUser(token)`. No session, or an unconfirmed email → 401; cross-site cookie → 403. `user_id` is only ever the verified user and is never a tool argument. `web/middleware.ts` returns early for exactly `/api/ledger-chat`, because its session gate would otherwise redirect the cookie-less native request to `/login`; the route re-applies the gates it bypassed (confirmed email in the caller guard; the profile gate in step 4).
3. **Consent.** The `settings_kv` key `consent.ledgerChatOptIn` must hold the current notice version (`LEDGER_CHAT_NOTICE_VERSION`, checked by `isCurrentChatOptIn`), read with the caller's own client; anything else, including a pre-versioning `true` or an older version, → 403 `consent_required` (see `docs/architecture/ledger-chat-consent-adr.md`). Opting out stores `false`. Every place that can turn it on shows the same notice, which lives in `src/domain/ledgerChat/notice.ts` (web re-exports it from `web/components/chat/notice.ts`): processor and country, every category sent, the discreet-mode exception, Anthropic's retention, device-only storage, a link to the policy. Those places are the panel's consent card on web, the confirm dialog behind web Settings › Privacy (shown only while `isLedgerChatEnabled()` is on), and the Ask screen and Settings › Privacy toggle on mobile. Each write records the audit event `ledger_chat_consent_toggled { enabled, privacyVersion, noticeVersion }` (category `privacy`), registered in `src/services/audit.ts`, `supabase/functions/_shared/auditAllowlist.ts` and `web/app/api/audit/schema.ts`; the versions record which policy and notice the consent rested on. Changing any of the words a reader sees before opting in (the web notice, the mobile device line `MOBILE_DEVICE_NOTE`, the Settings line) means bumping `LEDGER_CHAT_NOTICE_VERSION`: `web/__tests__/ledgerChatScope.test.ts` pins one sha256 of all three to the current version in an append-only map and fails with "bump LEDGER_CHAT_NOTICE_VERSION" otherwise. Web and mobile deploy separately, so ship both when the version changes; an older mobile build stores an older version (or a bare `true`) that the route refuses, and the reader is asked again after updating.
4. **Profile gates.** `loadProfile` (one row, caller's client), then a reader who is not onboarded → 403 `forbidden`, and an onboarded reader who needs a consent refresh (`needsConsentRefresh`: a missing stamp or an outdated version) → 403 `consent_outdated`, so the client points them to `/consent`. The last one fails closed on an old terms, privacy or medical version or a missing health-data consent, so a mobile build whose own consent gate has gaps still cannot reach the model. These run before a daily token is spent.
5. **Limits.** `checkRateLimits` (`web/lib/auth/rateLimit.ts`, service role, HMAC-keyed, fail closed) with two buckets: `ledger_chat_user` (`LEDGER_CHAT_DAILY_CAP_USER`, default 20 per day) and `ledger_chat_global` (`LEDGER_CHAT_DAILY_CAP_GLOBAL`, default 500 per day). A token spent on an upstream failure is not refunded. The hard money cap is the spend limit on the API key in the Anthropic console.

**The panel state (GET).** `GET /api/ledger-chat` serves the dock and the Ask screen. It passes the same flag, caller and profile gates, calls no model and needs no key, and spends its own bucket, `ledger_chat_state` (`LEDGER_CHAT_DAILY_CAP_STATE`, default 120 per day), never a question. It returns exactly `{ consented, discreet, hideTotals, currency, locale, starters }`. The web panel reads it on every open, not once per mount, because the dock outlives Settings changes (Hide totals, discreet mode, country) and a kept copy goes stale. Closing the panel forgets the state and any figure the reader revealed, and unknown state masks every figure; a refusal shown from an earlier open is dropped when the new read succeeds. The post-consent re-read applies only if no close or reopen has replaced that open's load. Without the opt-in it reads only the profile and returns no starters; with it, it loads only what the starters need (the daily summary, the active goals and one short log page for the mood and trigger check), never prices or goal history.

**What the chat may read, as one list.** `src/domain/ledgerChat/scope.ts` holds `IN_SCOPE` and `OUT_OF_SCOPE`. The system prompt renders both verbatim, the consent notice renders the one-sentence `IN_SCOPE_SUMMARY`, and `web/__tests__/ledgerChatScope.test.ts` pins them, so the promise and the instructions cannot drift apart. In scope: the reader's own entries for 90 days (time, sticks, brand, variant, price paid, purchase mode, moods, trigger, craving, situation, notes), daily totals for up to a year (never before onboarding) and what is computed from them, active goals with live state and proposals plus the history of paused, completed and abandoned goals, the prices recorded on entries in the last 90 days, the dates entries were edited (the values before an edit are not stored, so none are sent), and a short context line. Out of scope, never loaded and declined if asked: name, date of birth or age, gender, email, phone and place; sign-in, audit, error and usage records, consents, legal versions and settings other than discreet mode; anyone else's data; general knowledge, news, tobacco product advice and prices not in the ledger; medical advice and ways to quit; praise, scolding and nagging; anything older than the windows and forecasts beyond the spend outlook.

Reads run with the caller's JWT client, so RLS applies, in parallel: `loadLogsPage` (90 days, one page of up to `GOAL_WINDOW_LOG_LIMIT` = 2000 rows, the ceiling Home and Goals use), `loadDailySummary` (floored at onboarding, as Home), and `loadGoals` once for active goals and history together (a bounded read; `goal_history` hands the model at most 50). Edit dates and price history come from the logs already loaded (`updatedAt`, and `unitPriceInr` where the price source is exact or estimated; catalogue guesses are left out), so they add no query. The explicit-client loaders are used; the cookie-path `getServer*` wrappers never are (`web/__tests__/ledgerChatRouteGuard.test.ts` pins this and the gate order).

**What the model sees.** Tool outputs only, plus the reader-context block, built from an allowlist: `buildToolContext` copies only country, currency, baseline and the discreet flag, so no name, birth date, gender, email, phone or place can be reached. `src/tests/ledgerChatContext.test.ts` runs every tool with a fixture profile full of distinctive identity values and fails if any appears anywhere in the output. The twelve tools (`src/domain/ledgerChat/tools.ts`) are read-only wrappers over `src/domain`: `compare_periods`, `totals_in_window`, `savings`, `spend_outlook`, `when_and_why`, `brand_mix`, `goal_status`, `insights`, `recent_entries`, `goal_history`, `price_history` and `entry_edits`. `recent_entries` is the only one that returns raw entries (last 1–30 days, at most 200, no ids), fetched only when the model asks; `entry_edits` returns dates and hours, never values. Stored free text has no length limit in the database, so `buildToolContext` bounds it once before any tool runs (`cleanText`, `src/domain/ledgerChat/context.ts`): control characters become spaces, then trim and cap, at `NOTE_MAX_CHARS` (120) for notes and `TEXT_FIELD_MAX_CHARS` (60) for brand, variant, trigger, mood and context; text that is empty afterwards counts as absent. Every tool and the guard's name list therefore see the same bounded text, and one huge or hostile value cannot bloat every call or smuggle instructions. Each tool's rows keep a fixed id per tool, so when one tool is called twice in a turn ("September vs October") the turn engine keeps an exact repeat once and suffixes a different result `#2`, `#3` (`addRow`, `turn.ts`), which keeps the panel's React keys and reveal-on-tap state unique and stable. **In discreet mode, brand names are replaced with aliases and notes and variants dropped before any tool runs** (`aliasLogsForDiscreet`, `src/domain/ledgerChat/context.ts`; one aliaser per turn, so a brand has the same alias in every tool; the format ("Brand A", "Brand B", …) comes from the shared `brandAlias` in `src/lib/discreet.ts`). This is the one deliberate exception to DESIGN.md's "mask at the render site, never at the source" rule: the render site for this data is a third party, so the masking has to happen before egress. Row values on the client are still masked at render (`isHomeTotalsHidden`, tap to reveal), on mobile through `src/lib/discreet.ts` as well.

**What the model may say.** The system prompt (`web/lib/server/ledgerChat/prompt.ts`) forbids figures, links, markdown, medical advice and judgement, refuses the out-of-scope list, and declares tool results and entries to be data, never instructions. The turn engine (`web/lib/server/ledgerChat/turn.ts`) enforces the part prompts cannot: narration is sanitised to plain text (`sanitizeNarration`), and `findUnverifiedFigures` (`src/domain/ledgerChat/guard.ts`) checks both digit-runs and number words. A figure must exist in this turn's tool results or read as a time, a short duration or a day of the month. Digits in any script count: Devanagari, Arabic-Indic, fullwidth and the rest are folded to ASCII (`toAsciiDigits`) before the checks, so "५००" is as unverifiable as "500". A day of the month passes when a month name follows ("14 June", "14th of June"; English month names only, day before month). A decimal passes only if the tool results hold that exact value, so "18.40" is not excused by an "18" (the old rounding pass is gone). The tool results are harvested for figures with two exceptions: hour fields (`hour`, `entryHour`), whose clock times pass by their context, and `notes`, which are the reader's own words ("had 10 with Raj"), not ledger figures; an ISO date in a string contributes only its year. Number words count as figures: English cardinals above "two", hundred, thousand, lakh, crore and percent, and Hinglish ek to das, sau and hazaar, unless they sit in a duration or time context. "one", "two" and "zero" are ordinary prose outside discreet mode ("zero entries today") and never counted there. In discreet mode the panel's masking works on digits, not words, so the guard is stricter: every Hinglish digit word, "zero", "twice", "a couple of" and "a dozen" counts, and "one", "two" and "do" count before a unit ("two packs"). Because the guard knows English and Hinglish only, the system prompt tells the model to reply in English whenever brand names are aliases (discreet mode), whatever language the question was in. One retry, then the fixed fallback sentence with the rows. At most three model calls per turn; a `refusal` stop yields a calm fallback and runs no tools; unknown or invalid tool calls become `is_error` results, never throws.

**Where it appears.** Web: `AskLedgerDock` (`web/components/chat/AskLedgerDock.tsx`) is mounted once in the `(app)` layout. On Dashboard, Trends, History, Goals and Settings it shows a docked "Ask the ledger…" box bottom-right on desktop, or an "Ask" pill above the bottom nav on a phone, and Enter opens the panel with the typed question. The panel manages focus itself: on open it lands in the question box (not the first tabbable, which would be Clear conversation once there are turns), falling back to the dialog while an answer is in flight; on close it returns to whichever dock control opened it (`returnFocus`); when an answer finishes it goes back to the box unless the reader moved elsewhere, and never on touch, where it would raise the keyboard. The newest answer is mirrored into the polite live region as hidden text with the same masking as the visible prose but spoken as the word "hidden" (`spokenMask`, not the "•••" glyph a screen reader would read as "bullet bullet bullet"), so it never speaks a figure discreet mode hides. It hides itself on `/log` and below (`isDockHidden`) and is not mounted on onboarding, `/consent`, legal or public pages, which sit outside the `(app)` layout. It can be folded away; that choice is the device preference `sl_chat_dock_minimised` (`web.chatDockMinimised` in the registry: not personal, so no lifecycle event clears it). Opening it sends `ledger_chat_opened { surface, page }` under the analytics opt-in, with no question text. Mobile: the `/ask` modal screen (`app/ask.tsx`), opened from `AskPill` in `app/(tabs)/_layout.tsx` on Home, Trends, History, Goals and Settings but not Log (an allowlist in `src/lib/askPill.ts`), through the thin client `src/services/ledgerChat.ts`, which calls `${EXPO_PUBLIC_WEB_BASE_URL}/api/ledger-chat` with the session token as Bearer. The Ask screen lifts the composer above the keyboard (`KeyboardAvoidingView` offset by the measured top of the sheet; `height` on Android), scrolls to the end on new content (animated unless reduce-motion), speaks each new answer with `AccessibilityInfo.announceForAccessibility` using `answerAnnouncement` (the drawn masking, spoken as "hidden"), and leaves through `leaveTarget`: back when there is a screen to go back to, else `/(tabs)`, so a cold start from `smokeledger://ask` can still close. A server `consent_required` does not mark the waiting question as sent (`waitingTakenAfter`), so it goes out after the next opt-in. In Settings the switch shows saved state only: turning it on opens the notice and saves nothing until "Turn on", and turning it off with nothing saved just closes the notice, with no setting or audit row.

**What is stored and logged.** Nothing server-side: no chat table, so `export_account_data`, `erase_account_data` and `verify:sovereignty` are unchanged. On web the conversation lives in the browser's `localStorage` (`ledger-chat:v1:<userId>`, last 20 turns; the panel finds the user id through `sessionUserId`, which never rejects, so a failed session lookup opens an empty transcript instead of an unhandled rejection) and is cleared by the lifecycle registry on every null session (`AuthProvider`: `SIGNED_OUT`, expiry, deletion, and a browser reopened without Remember me), on Erase data, on Delete account, on consent withdrawal, when chat consent is turned off, and when discreet mode is turned on. On mobile the transcript is component state only: it holds no device store, nothing is written to storage, and closing the screen clears it (`privacy-promises.test.ts` checks that the Ask screen touches no storage). The panel labels every answer "Written by AI" and offers a plain "Clear conversation" control on web that empties the transcript at once; `clearTranscript` bumps a counter (`transcriptClearCount`), and an answer that was in flight when any clear ran (Clear conversation, sign-out, discreet on, chat turned off) is dropped instead of saved, so the device is as empty as the policy says. The counter is per tab; a clear in another tab is not seen. A consent write that finishes after the panel was closed sends no question. A `consent_required` from the server keeps the consent card: only the GET (the server saying consented) retires a card from an earlier open, never the panel's own optimistic flag. Server logs carry tool names and token counts only (`api.ledger_chat.turn`), never the question, the answer or the user id. The usage event `ledger_chat_asked` records `{ starter, tools }` under the analytics opt-in. Anthropic's processing (US, no training, limited retention) is disclosed in both privacy policies; the V3 page and policy name the goal history, the prices from entries and the edit dates, and say the feature is on web and mobile. `LEGAL_VERSIONS.privacy` is not bumped yet, so the notice is ahead of the published policy until the bump: production stays off until then (`docs/legal/owner-actions.md` section 8).

### Discreet mode: masking at the render site

Discreet mode is a privacy control against someone looking over the reader's shoulder or at a screen reader's output, not against the server. The server and the loaders always hand the client real values; every place a figure or brand name is *rendered* passes it through the pure helpers in `src/lib/discreet.ts` (`maskCount`, `maskInr`, `maskNumbers`, `maskBrandAt`, `brandAlias`, `lastEntryLabel`). The one exception is the chat, whose render site is a third party (see above).

On the Trends screen the render sites are not only the visible text. Every chart takes a formatter that covers each of its channels: the tooltip, the screen-reader data table, and, where the chart has one, its axis, visible bar values, `aria-label` and SVG `<title>`s (`LineChart` and `BarChart` are `aria-hidden`, so they have no label of their own):

- `LineChart` and `BarChart` pass `formatY` to the tooltip and to `ChartDataTable`, the visually hidden `table.sr-only` that screen readers read instead of the drawn chart (value and cap cells both). `BarChart` shows a Y axis whenever `formatY` is passed unless `showYAxis={false}`; the Trends hour-of-day chart passes `showYAxis={false}`, so its axis stays hidden whether discreet is on or off (nothing may change with discreet off).
- `BarChart3D` formats the visible per-bar count and the chart's `aria-label` (`formatValue`).
- `Heatmap` formats the per-cell `<title>` and the summary `aria-label` (`formatCount`); the busiest hour's clock time stays, because a time is a pattern, not a count.
- `Donut` formats slice values and names in the tooltip and table (with discreet off these now show compact money, such as ₹1.2K, rather than the raw figure) (`formatValue`, `formatLabel`). Its tooltip formatter reads a `sliceIndex` stamped on each datum and fails closed: if a label formatter is given but the index is missing it uses index −1, which `brandAlias` turns into "Brand hidden", never the raw name.
- The brand list and the donut use `brandRows` (`src/domain/brandRows.ts`, re-exported at `web/lib/trends/brandRows.ts`). Brand names become distinct aliases by display order, "Brand A", "Brand B", … then "Brand 27" and on, never one shared label, so rows stay readable and React keys stay unique (the key is the index under discreet, so no real name reaches the DOM). The share column masks to a bare "•••" with no "%".
- The Home "last entry" label (`lastEntryLabel`, `src/lib/discreet.ts`, used by mobile Home and web `QuickLogStrip`) shows only the masked brand under discreet; the variant is dropped, because a variant name can identify the brand.

Mobile mirrors this: the Trends deck reads "Period totals — hidden." and the "Around X a day" caption masks its figure (`headlineDeck`, `avgLine`, `src/domain/trendsCopy.ts`); the hour and weekday charts take `formatY`; `MoodTriggerMatrixView` takes `formatCount` for the pair and cell counts; and the brand list uses the same `brandRows`. The smoke-free streak stays visible everywhere, by design.

## Invariants

These rules must not break:

1. All 13 public base tables have RLS enabled. A new table that stores user data must have `ENABLE ROW LEVEL SECURITY` in its migration before the migration lands on production.

2. Every SECURITY DEFINER function in `public` must pin `search_path` explicitly. `search_path = ''` is the default; any deviation requires a written justification in the migration comment (see the two exceptions above).

3. `rate_limit_counters` must have no RLS policy. Its protection is the absence of any policy — default-deny — combined with `EXECUTE` being restricted to `service_role` on `consume_rate_limit`.

4. `record_audit_event` must not be callable by `authenticated`. The grant history in `20260521000000_audit_export_ops.sql:295–297` and `20260531075255_lockdown_secdef_execute.sql:33–39` enforces this; any migration that re-grants `EXECUTE` to `authenticated` would be a regression.

5. `compliance.delete` rows in `error_events` must have `user_id = null`. The CHECK constraint `error_events_compliance_delete_null_user_check` enforces this at the DB level. Do not drop this constraint.

6. `erase_account_data` must be called before `auth.admin.deleteUser`. If the erase fails, deletion must abort. The ordering in `delete-account/index.ts:186–213` enforces this.

7. `AUDIT_PEPPER` must never appear in source code, logs, or environment variables accessible to client bundles. It lives only in the Edge Function secrets dashboard and in the `app.audit_pepper` GUC (which is set per `docs/runbooks/audit-pepper-rotation.md`).

8. The `v_daily_summary_user` view must have `security_invoker = true` so that RLS on the underlying `cigarette_logs` table applies when authenticated users query it directly. Set in `supabase/migrations/20260602000000_perf_rls_initplan_indexes.sql:57`.

9. Nothing reaches the AI processor before the kill switch, the caller guard, the consent key, the profile gates (including `consent_outdated`) and the rate limits have all passed, in that order, and the reads behind it run on the caller's JWT, never the service role (`web/__tests__/ledgerChatRouteGuard.test.ts`).

10. The chat never stores prompts, answers or transcripts server-side, and never logs them. If a chat table is ever added it must join `export_account_data`, `erase_account_data` and `verify:sovereignty` in the same change.

11. Every figure the chat shows comes from a tool result; narration that states a figure the tools did not produce is rewritten or replaced (`src/domain/ledgerChat/guard.ts`, `web/__tests__/ledgerChatTurn.test.ts`). Digits in any script count as digits, and a decimal must match a tool figure exactly. Discreet readers' brand names are aliased and their notes and variants dropped before egress, and they get English replies. Number words count as figures; in discreet mode the guard is stricter (every Hinglish digit word and "zero" always, "one", "two" and "do" before a unit). Free text is cleaned and capped before any tool reads it (`cleanText`).

12. In discreet mode no chart renders a raw count, amount or brand name in any channel a reader or screen reader can reach: visible text, tooltip, `aria-label`, SVG `<title>`, sr-only table cell, or React key. A new chart or table takes a formatter and passes it to all of them; a masked heading over an unmasked table is a leak (`web/__tests__/chartMasking.test.ts`, `chartDataTable.test.ts`, `src/tests/discreet.test.ts`, `brandRows.test.ts`, `trendsCopy.test.ts`).

13. A sign-in never deletes an account. The re-auth detour returns to a confirmation (`DELETE_RESUME_PATH`), and only that confirmation's button calls `deleteUserAccount`. Cancelling it must state that nothing was deleted. On mobile the confirmation opens only against an unexpired (10 minutes), per-user `mobile.deleteIntent` record written before the detour and consumed on first read, so a crafted deep link cannot raise it (`src/tests/reauth-route.test.ts`, `deleteUserAccount.test.ts`).

14. Every store that can hold something about a reader has a row in `STORES` and a clearer; a store cannot be added without a policy (`src/tests/lifecycle.test.ts`, `web/__tests__/clearDevice.test.ts`). The auth cookies (web) and the stored session (mobile) are cleared only on an explicit `SIGNED_OUT`; on web, any other null session still clears the localStorage stores.

15. The export holds everything erase removes (the sign-in record and the user's own error reports included), and erase leaves nothing personal behind except the disclosed erasure-proof audit tier (`src/tests/export-complete-migration.test.ts`, `erase-auth-metadata.test.ts`).

16. Records are deleted on the stated schedule and no sooner without the reader's action: audit and usage events at 12 months, error reports at 90 days, rate-limit counters at 2 days, nothing for inactivity. The text and the SQL read the same `RETENTION` numbers.

17. No `error_events` text is stored unredacted: every writer goes through `redactText` / `redactRoute`.

18. The re-consent gate never loops: `/consent` and the paths needed to read, export, withdraw and sign in are exempt, and a current reader on `/consent` is sent home. Health-data consent is never pre-ticked or backfilled, and declining is the same size as accepting.

19. What the chat may read is the list in `src/domain/ledgerChat/scope.ts`, rendered into the prompt and the notice and pinned by tests. The tool context is built from an allowlist, so identity (name, date of birth, gender, email, phone, place) and account machinery never reach the model.

## Edge cases and gotchas

**Marketing consent is locked empty, by a trigger.** `marketing_consent_at` is never written by the app, and the BEFORE INSERT OR UPDATE trigger `trg_user_profiles_marketing_consent_null` (`public.null_marketing_consent_at()`, `20261105110000_marketing_consent_null_trigger.sql`) forces it to NULL for every role, because the row-wide `user_profiles` UPDATE policy would otherwise let any client set it. It replaced a CHECK (`user_profiles_marketing_consent_unused`, dropped by the same migration) that made an older mobile build's consent write fail with 23514: that build sends `marketingConsentAt` in the same update that stamps the consent versions, and there are no over-the-air mobile updates. With the trigger the write succeeds and the column stays empty. The function is `SECURITY INVOKER`, pins `search_path = ''` and is revoked from everyone (a trigger function needs no EXECUTE at fire time). Stamps the old mobile screen wrote from the analytics checkbox were cleared with a per-user, server-only `marketing_consent_cleared` audit row (ADR `docs/architecture/marketing-consent.md`). Shipping a real opt-in means dropping the trigger and function in the same migration. `scripts/sql/smoke.sql` fails CI if the trigger is missing or the CHECK is back.

**Erase vs delete are different operations.** "Erase data" wipes product tables and anonymizes audit rows but keeps the auth identity — the user can log back in and re-onboard. "Delete account" removes the auth identity entirely. Callers that conflate the two will produce confusing UI; the distinction is documented in `docs/deployment/production-ops-checklist.md:200–204`.

**`erase_account_data` must run as the user, not as service-role.** The function reads `auth.uid()` internally. Calling it with a service-role client would yield `auth.uid() = null` and the function would raise `42501`. The Edge Function deliberately passes the user's bearer token (`supabaseUser.rpc('erase_account_data')` at `delete-account/index.ts:183`).

**Anonymized audit rows are invisible to the user after erase.** Once `erase_account_data` nulls out `user_id`, the SELECT policy (`user_id = auth.uid()`) can no longer match those rows. An export performed after erase shows only the one `account_data_erased` row, which is still attributed to the live user until the account itself is deleted. This is correct behavior, not data loss.

**The compliance delete audit insert is best-effort.** The `try/catch` at `delete-account/index.ts:157–173` catches audit insert failures and logs a warning rather than aborting. A failed audit insert means the compliance record may be missing, but the user-requested deletion proceeds. This is intentional: the alternative — blocking account deletion because the audit table was temporarily unavailable — would be a worse outcome for the user.

**Export pagination uses a `(ts_utc, id)` composite cursor, not a numeric offset.** This is stable under concurrent inserts. An offset-based cursor would drift if new rows were written during a multi-page export. The cursor semantics are defined at `supabase/migrations/20260521000000_audit_export_ops.sql:62–65`.

**The error_events INSERT policy was tightened twice.** The initial policy in `20260519100000_hardening_and_compliance.sql:68` allowed `user_id IS NULL OR user_id = auth.uid()` (permissive). It was replaced in `20260520000000_security_correctness.sql:254–255` to require `user_id = auth.uid() AND category <> 'compliance.delete'` (restrictive). The CHECK constraint was added in the same migration. Any audit of the policy history should be read in migration order.

**The log rate limit counts on `created_at`, not `ts_utc`.** Backdated logs (up to 24h) made `ts_utc` user-controlled, so counting the 50-per-hour window on it let a user evade the cap by backdating every insert. `supabase/migrations/20260626120000_rate_limit_window_created_at.sql` moved the window to the server-set `created_at`. Own-account abuse only, but it protects free-tier write volume.

**The `v_daily_summary_user` view had an RLS bypass until migration `20260602000000`.** Before that migration added `security_invoker = true`, the view ran with owner privileges and bypassed RLS — a signed-in user could read any other user's daily aggregates by querying the view directly with a `user_id` filter. The fix is in place. The `get_daily_summary` RPC path was never affected (it filters by `auth.uid()` explicitly), but direct PostgREST access to the view was the hole.

## Open gaps

**The V3 privacy work is not live.** The five migrations (`20261104100000` to `20261104140000`) are unapplied until the owner reviews and applies them, so on the live project erase still leaves the sign-in record, error reports are kept as they were, no purge runs, and the health-consent column does not exist. `LEGAL_VERSIONS` is not bumped, and will not be until the EU representative is named in `src/lib/legalEntity.ts`; the release gate is the owner's, and `src/tests/legal-release-gate.test.ts` fails if the versions move without a named representative. Nothing here was run against a local `supabase db reset`.

**The marketing-consent trigger is not confirmed live.** `20261105110000_marketing_consent_null_trigger.sql` is in the repo and proven by `src/tests/marketing-consent-null-trigger-migration.test.ts` and `smoke.sql`, but nobody has verified it on the live project. Until the owner applies it, the live CHECK from `20261102120000` still stands and an older mobile build that ticks analytics fails the consent write with 23514. Apply it before, or with, the next mobile release.

**Web withdrawal still records client-side, and before the action.** Only mobile moved to "record after success" (erase) and "server writes it" (delete). Web Settings still calls `recordConsentWithdrawal` before the erase or delete, so a web withdrawal that is then cancelled or fails can leave a `consent_revoked` row for something that did not happen. `deleteUserAccount` already accepts `withdraw`, so the fix is wiring web to it and to `recordWithdrawalAfter`.

**The mobile delete record is a deep-link guard, not authentication.** It stops a link from raising the prompt; the real gate is still the server's re-auth check (`hasRecentSignIn`) plus the reader tapping the confirmation. If SecureStore is unavailable the detour is refused, so delete is blocked on such a device (fail closed); carrying the proof in the login route param is the recorded upgrade if that bites.

**The chat's date and language coverage is English.** A day of the month passes only before an English month name ("14 June"); "June 14", "14 juin" and "14 जून" take the retry, as does the 8 in "8–14 June". The number-word lists are English and Hinglish, which is why discreet replies are forced into English. Per-language lists in `guard.ts` are the upgrade.

**The `discreetOn` lifecycle event is not fired through the registry.** Turning discreet mode on does clear the saved chat transcript (it may hold real brand names), but web Settings calls `clearTranscript()` directly (`onToggleDiscreet`) instead of `clearWebDevice('discreetOn')`. The registry row and the behaviour agree; the two paths are just not the same code, and the mobile transcript is memory-only, so there is nothing to clear there.

**Ask the ledger is built but not on.** Production has no key and `LEDGER_CHAT_ENABLED=false`; the mobile flag is off in every build. The notice already lists goal history, prices from entries and edit dates, ahead of the published policy, so no opt-in should be recorded before `LEGAL_VERSIONS` is bumped. The code now enforces that on its own: Production stays off, and release builds of mobile stay off, until `LEGAL_VERSIONS.privacy` moves past `2026-11-02` (and that waits on the EU representative). Opt-ins recorded earlier as a bare `true` or an older version read as off; nothing is migrated. From now on Preview stores the current notice version, and Preview shares the Production database, so those opt-ins will count in Production after the bump unless the notice changes before then. The notice hash and version are only as good as the discipline of bumping both mobile and web together. The `audit-record` redeploy, the live probe (identity and medical refusals, discreet, a Hinglish number) and the manual Expo check are owner steps in `docs/legal/owner-actions.md` section 8. `eas.json` ships a blank `EXPO_PUBLIC_WEB_BASE_URL`, which the mobile client treats as a misconfiguration.

**Questions for a lawyer, recorded not decided.** The DPDP start date; whether smoking logs are health data in law (they are treated as such here); whether a ticked box counts as the "written" consent the SPDI rules ask for; CERT-In 6-hour reporting (not built into the breach runbook); and the DPDP Rule 8(3) one-year floor against erasure on request (content is erased at once and only the 12-month audit tier is kept). The Hindi notice and a way to request other Eighth Schedule languages are a recorded follow-up before May 2027.

**Discreet-mode leftovers, recorded not fixed.** The heatmap's busiest hour ("at 15:00") stays visible under discreet mode: it is a pattern, not a count. The mobile captions "A flat line." and "A sparse window" stay too: they carry no digits and match web. The mobile wiring that passes each formatter to the Expo chart components has no automated test (only the pure helpers `brandRows` and `trendsCopy` do). The strengthened discreet e2e in `responsive.spec.ts` needs a seeded local Supabase, so it runs only in CI, not on a developer machine without `web/.env.e2e`.

**`app.audit_pepper` was found unset on the live DB (2026-07-05).** The pepper guard (below) is live, so every `erase_account_data` call currently fails with `P0001` until the operator runs `ALTER DATABASE postgres SET app.audit_pepper = '<AUDIT_PEPPER value>'` in the SQL editor. This is fail-closed working as designed — erasure is blocked rather than writing a reversible hash — but it means the DPDP erase right is unavailable until the GUC is set. Tracked as an open operator action.

**Leaked-password protection is a dashboard toggle, not enforced by code.** The Supabase advisor flags `auth_leaked_password_protection` as a WARN because the toggle must be enabled manually in the dashboard (Authentication → Security → Password Strength). It cannot be set via migration. The ops checklist tracks it (`docs/deployment/production-ops-checklist.md:§2`), but there is no automated gate that fails the build if it is off.

## Resolved gaps

**AUDIT_PEPPER guard added** (`supabase/migrations/20260629000000_erase_pepper_guard.sql`). `erase_account_data` now raises `P0001` immediately if `current_setting('app.audit_pepper', true)` returns an empty string, preventing a trivially reversible audit hash on freshly linked CI/staging projects where only the Edge Function secret is configured.

**Stale spec manifest resolved.** `web/lib/server/auth.ts` did not exist — the web app's server-side auth logic lives in `web/middleware.ts` (session gate, consent funnel, CSP), `web/lib/supabase/server.ts` (server Supabase client), `web/lib/supabase/admin.ts` (service-role client), and `web/app/auth/callback/route.ts` (OAuth/magic link callback). The `sources:` frontmatter has been updated to reflect the real files.

**The `compliance.delete` CHECK constraint discrepancy is resolved.** The June 2026 sovereignty audit marked `error_events_compliance_delete_null_user_check` as absent (MEDIUM finding) — correctly: the `20260520000000` constraint block was edited post-apply and never reached live. `20260619000000_error_events_compliance_check.sql` restored it; re-verified live via `pg_constraint` on 2026-07-06. The finding is closed.

### Hardening, 2026-10 (security scan and review follow-ups)

- **Logs are written only through the rate-limited RPC.** `cigarette_logs` has SELECT / UPDATE / DELETE policies and no INSERT path for `authenticated` (`20261031000000_logs_insert_via_rpc.sql`), so `create_log_with_rate_limit`'s cap cannot be bypassed through PostgREST. UPDATE is granted only on the logged fields, so back-dating `created_at` (the cap's window) is denied too. Proven by `smoke.sql` (table and column privileges) and by RLS integration tests: a direct insert and a `created_at` rewrite both get `42501`, while an ordinary edit succeeds.
- **anon default-deny** on every public table, sequence and function, now and for new objects (`20261030000000_security_hardening.sql`).
- **Legal pages render per request.** `/privacy`, `/terms` and `/support` were `force-static`, so their inline Next scripts carried no CSP nonce and were blocked; they are `force-dynamic` now. The e2e smoke suite fails on any CSP violation on a public route.
- **Headers.** `img-src` is `'self' data: blob:` (no `https:` wildcard); `Cross-Origin-Opener-Policy` and `Cross-Origin-Resource-Policy` are `same-origin`; `/auth/confirm` sends `Referrer-Policy: same-origin`.
- **Phone sign-in is opt-in** (`NEXT_PUBLIC_PHONE_OTP_ENABLED` must be exactly `true`), because `send-sms-otp` is not deployed.
